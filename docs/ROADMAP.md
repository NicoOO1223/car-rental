# Roadmap

Status as of 2026-09-28. Update this file whenever a layer ships or a decision changes. Until now the layer scheme lived only in planning sessions and commit messages, so treat this as the single record.

## Direction

The product is being built to sell to other rental operators.

- **Customer:** independent rental operators (B2B).
- **Hosting:** one separate stack per customer first. True multi-tenancy is deferred until real customers exist.
- **Email and SMS:** deferred by decision.
- **Storefront:** a public booking site for renters is in scope.

The earlier layers assumed an internal, staff-only, single-business tool. That assumption no longer holds for the storefront or for per-customer business identity.

## Next layers

Each layer gets its own planning pass that re-explores the code before any build starts.

**L12 Production hardening.** Built. Nothing below is live until it is pushed and the deployment checklist is done.
- Perimeter: the database no longer accepts the internet. The backup job opens a firewall rule for its own runner and removes it. Containers run as non-root with health checks. Docs are off in production, security headers are on for both API and frontend (the frontend CSP is Report-Only for now), and CORS is limited to what the app uses.
- Secrets and access: the signing key is generated by the bootstrap script. The app can use a database role that cannot change the schema, with migrations run by a separate login.
- Auth: five wrong passwords lock an account for 15 minutes, with a per-IP budget on top. Password reset, deactivation and role changes revoke existing sessions. Deactivated accounts cannot log in.
- Payments: a signed Stripe webhook with event dedupe, one shared rule set for payment state (a refunded or succeeded payment never moves backwards, which also fixes confirm-payment resurrecting a refunded booking), idempotency keys on creates, refunds and captures.
- Performance: indexes on the hot queries, connection pool settings, availability in one query, cheaper dashboard, server-side paging and search for reservations and customers, and one request for the fleet timeline.
- Quality: the test suite runs on its own `_test` database and refuses any other. CI uses the production Postgres major, deploys are smoke-tested, Dependabot and a weekly dependency audit are on, and the repo has a root README.
- Monitoring: health and readiness probes, plus alert rules for restarts, server errors, database CPU, storage and failed connections.

Not done, on purpose:
- **Private database network.** The database still admits Azure services broadly (the Container Apps outbound IPs are too many to allow-list). A VNet with a private endpoint is the full fix and needs its own change.
- **Staging environment.** Moved to L14: the operator's own demo stack becomes the canary that deploys first.
- **Pagination for the remaining lists** (cars, maintenance, users). They are small and bounded by the size of the business.

Deployment checklist, in order:
1. Push. The deploy runs the migrations and the smoke test.
2. Delete the old internet-wide firewall rule `AllowGithubActionsRunners` on the live server, and give the GitHub identity the firewall role (`bootstrap.ps1 -BackupPrincipalObjectId`). Run the backup workflow once by hand to confirm it still works.
3. Apply the health probes to the live backend (re-run `bootstrap.ps1`, which sets them).
4. Deploy the alert rules with `-AlertEmail`.
5. Create the runtime database role and switch to it with `-UseAppRole`.
6. Register the Stripe webhook endpoint (`/api/stripe/webhook`, events `payment_intent.*`) and store its signing secret as `STRIPE_WEBHOOK_SECRET`.
7. Once a customer is paying: set `-BackendMinReplicas 1` (roughly 10 to 15 USD a month).
8. After a period of clean reports, change the frontend CSP from Report-Only to enforcing.
9. Scan the database from outside to confirm it does not answer.

**L13 Business profile and localization.** Built. Nothing below is live until it is pushed.
- Business profile in Configuration: name, legal name, address, phone, email, VAT ID, timezone, formatting locale and agreement terms, plus an uploaded logo stored in the database. A public branding endpoint lets the sign-in page show the name and logo. The sidebar, sign-in page, tab title and agreement all use them; nothing hardcodes "Car Rental" any more.
- Locations are administered in the app: add, edit and retire. Each has its own timezone. A location still holding vehicles or open reservations cannot be retired, and new bookings cannot use a retired one.
- Days follow timezones instead of UTC: the dashboard's today counts, revenue by day, fleet status for a date, reservation day filters, maintenance and inspection dates. The booking wizard and edit modal turn "10:00" into an instant using the pickup or return location's timezone, which fixes bookings made from a different timezone than the airport. Times, dates and money follow the business locale.
- Identity is country neutral: a national ID number is optional (an ID document number also identifies the customer), the PESEL checksum only runs for a Polish customer who enters one, and the country list is every ISO country in the business language.
- VAT and invoices: one VAT rate, with prices either including VAT or having it added. A rental payment issues a numbered invoice in the same transaction, from whichever path records it. Numbers come from a locked counter, so the sequence has no gaps. An invoice copies the seller, customer, lines and amounts, and never changes. A refund issues a credit note.

Decisions and gaps to know about:
- **Return charges are not invoiced.** Late fees, fuel and damage charges take payment but produce no invoice, because how VAT applies to them (damage compensation in particular) is a question for an accountant. Payments taken before this shipped also have no invoice, and refunding one issues no credit note.
- Only formats follow the locale in L13. The words are translated by L13b below.
- The fleet timeline draws days by the viewer's own calendar and the business "today". A day with a clock change can be an hour off in that drawing only.
- One VAT rate for the whole business, not per item.
- Invoice numbers are one series with a configurable prefix, and credit notes share the sequence under the prefix CN. Some countries require a separate or yearly series; confirm before the first customer.
- Historic records keep their times: naive timestamps written before this were UTC, and are still read as UTC.

Deployment notes:
1. Push. The migrations run at start and change no behaviour: timezone stays UTC, VAT stays 0, the brand stays "Car Rental".
2. As an admin, open Configuration, Business and set the name, details, timezone (Europe/Rome for the Sardinia data) and format. Set each location's timezone under Locations.
3. Set the VAT rate and price setting once you know them. The first invoice number starts the sequence.

**L13b Interface and document language.** Built. English, Italian and Polish. Nothing below is live until it is pushed.
- Each person picks their own interface language in the sidebar (labelled "Language", not "Settings"), saved on their account. This is the first item of the future personal-preferences layer. A business default, set under Configuration, Business, applies to anyone who has not chosen, and to the sign-in page for a first visit. A signed-in person never inherits the language another person used on the same device.
- Every screen reads its text from `frontend/messages/{en,it,pl}.json`: whole sentences with plural forms (Polish has four), so nothing is glued together from fragments. Statuses, roles, categories and audit actions show translated names while the stored values are unchanged. A missing translation shows English, never a bare key.
- Server errors carry a stable code and their values (`{detail, code, params}`), and the interface words them in the reader's language. The English `detail` stays for other clients, and a test fails if a service raises a sentence without a code.
- Printed documents use a separate business document language. The agreement follows the current setting. An invoice is stored with the language it was issued in, so a reprint never changes, and a credit note uses its invoice's language. Documents use the bundled DejaVu Sans, since the built-in font cannot print Polish letters. Dates keep the year-first layout with the zone name in every language, on purpose, so they cannot be misread.
- CI runs `npm run check:messages --strict`: the three catalogs have the same keys and placeholders, every key used in code exists and is given the values it needs, every server error code has a message, and no text is left hardcoded in a screen. A development-only pseudo-language (`Pseudo (dev)` in the picker) marks every extracted string, so unextracted text is easy to spot.

Decisions and gaps to know about:
- **Italian and Polish were drafted by Claude and have not been reviewed by a native speaker.** This matters most for the agreement and invoice wording, which can carry legal weight. Some countries require specific phrases on invoices; confirm before the first real invoice.
- **Dates on screen follow the business format, not the interface language.** Set the business format under Configuration, Business (for example Italiano) so weekdays and months are worded to match.
- Extras' names and descriptions are business data, so each extra has optional Italian and Polish wording in its edit form, and English is the fallback for any field left empty. The starting extras come with Italian and Polish wording from the migration. Screens, bookings, the agreement and invoices use the wording for the language showing (the document language for printed documents).
- A custom agreement text is printed exactly as the admin wrote it, in whatever language that is.
- Not covered: languages beyond these three (adding one is a catalog file, see `docs/TRANSLATING.md`), and right-to-left layout.

Deployment notes:
1. Push. The migrations default everything to English, so nothing changes on deploy.
2. As an admin, set the default interface language and the document language under Configuration, Business.
3. Have a native Italian and Polish speaker review the catalogs (`docs/TRANSLATING.md`) before customers rely on them.

**L13c Fleet cost, insurance and notifications.** Built. Nothing below is live until it is pushed.
- A maintenance task can carry a cost, typed in when it is logged and replaceable when a technical inspection is completed. Empty means not entered, not zero. The maintenance list and each vehicle's history show it. This is the input for the cost tracking to come.
- A vehicle has an insured-since date, an insured-until date and an insurance cost for that period, edited with the rest of its condition.
- Notifications are worked out from the data each time, never stored: a vehicle away from its home airport, an inspection due soon or overdue, insurance ending soon or ended. A bell in the sidebar shows the count (red when something is urgent) and opens a list that links to each vehicle. Items disappear when the thing is fixed, so nothing needs marking as read. The lead time is Configuration, System, "Reminder window (days)", 30 by default.
- Notifications are in-app only. Email and SMS stay deferred with L9, so nobody is told unless they open the app.
- Not covered: a cost on cleaning or non-inspection completions beyond what was entered when logging, and cost reports.

**L14 Per-customer stack automation.**
- Parameterize the Bicep and bootstrap script by customer, with one shared registry and one image for all stacks.
- Move the frontend from build-time to runtime configuration so a single image serves every stack.
- Deploy through a manifest of stacks, with the operator's own demo stack as the canary, and run backups and restore drills per stack.
- Provision a stack with one command: infrastructure, migrations, first admin, customer Stripe keys and a smoke test.

**L15 Public storefront.**
- Add public routes outside the auth guard with an explicit allowlist, and unauthenticated availability, quote, booking and payment endpoints.
- Add rate limiting and bot protection. Unpaid online bookings must expire, because pending reservations block availability and spam could lock the fleet.
- Take payment at booking through webhooks, support guest checkout, capture consent and show a privacy notice, and apply operator branding from L13.
- Confirm on screen with a booking reference and a lookup page until email exists.
- Open questions: auto-confirm on payment versus staff confirmation, and whether the storefront is a route group in the existing app.

**L16 Legal pack.** Not code, and can start now. Terms of service, privacy policy, data-processing agreement, real rental agreement copy and storefront terms.

## Deferred

- Email and SMS (L9). Staff invites and password resets stay admin-driven, receipts and reminders do not exist, and the personal Settings layer stays blocked.
- True multi-tenancy, which becomes relevant after several customers exist.
- In-product billing for the SaaS itself. Invoice the first customers manually.
- The broader visual redesign (L11).

## Naming rule

Admin-editable business rules are called **Configuration**. The name **Settings** is reserved for a future user-facing layer covering personal preferences, notification preferences and self-service data deletion, which needs email delivery first.

## Definition of done for the first customer

- A fresh stack provisions from scratch in one command and passes a smoke test.
- A second stack with a different currency, timezone and branding runs correctly beside the first.
- Every stack restores from its own backup in the drill.
- The hardening checklist passes, including an external port scan of the database.
- A storefront booking completes end to end with a real Stripe test payment confirmed by webhook, including the abandoned-tab case.
- A booking that is never paid expires and frees the car.
